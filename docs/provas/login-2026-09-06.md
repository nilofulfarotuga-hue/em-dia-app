# Prova — entrar por e-mail arranjado (2026-09-06, 11h05 Lisboa)

O Danilo disse: *"n esta dando para entra com email"* e, depois:
*"a tela ficou travada por tinha chegado o cd 8 digito depois voltei e n vai mais"*.

## A causa, encontrada e provada

O servidor mandava um código de **8** números e o campo da app só deixava
escrever **6**. Ninguém conseguia entrar. Quem voltava atrás para pedir outro
batia no limite de 1 minuto do servidor e recebia uma frase que só dizia
"não consegui entrar" — daí a sensação de ecrã preso.

Leitura literal da configuração do servidor, antes de mexer
(`GET https://api.supabase.com/v1/projects/tgdmgtmknbwhcqoxtjbs/config/auth`):

```
otp length -> 8
confirm subject -> Confirm your email address
confirm has Token -> false
magic has Token -> true
host -> smtp.resend.com
sender -> em-dia@boraguarda.com
```

E o e-mail que chegou mesmo à caixa, às 10:59:13 UTC, com 8 números:

```
assunto: O teu codigo do Em Dia
"Escreve este codigo na app: 12521272"
```

Havia ainda um segundo problema: quem entrava pela primeira vez (conta nova)
recebia o modelo **Confirm sign up**, que mandava um *link* e não o código.

## O que se mudou no servidor

`PATCH .../config/auth` → **HTTP 200**. Leitura de volta:

```

confirm subject -> O teu codigo do Em Dia
confirm has Token -> true
confirm has link -> false
magic has Token -> true
site -> https://app-em-dia.pages.dev
host -> smtp.resend.com
```

## O que se mudou na app

- O campo do código aceita de 4 a 8 números (era exactamente 6). Se o servidor
  voltar a mudar de tamanho, a app continua a funcionar.
- Casinhas para os números, envio automático quando o código enche, colar e
  preenchimento automático a funcionar.
- Cada erro tem a sua frase: e-mail torto, sem internet, códigos a mais,
  código curto, código errado, código fora de validade.
- Um relógio conta o minuto até se poder pedir outro código, em vez de deixar
  levar um "não consegui entrar" sem explicação.
- "Escrevi o e-mail errado" passou para cima, ao pé do e-mail — em baixo ficava
  fora do ecrã nos telemóveis pequenos, e era aí que a pessoa ficava presa.

## Duas coisas que só apareceram por ter entrado a sério

**1. O splash podia rodar para sempre.** Se o perfil não carregasse depois do
login, `app.dart` mostrava o mesmo splash de sempre e não havia saída. Agora
`PerfilStore.carregar` tem prazo de 20 segundos e o ecrã separa "a carregar"
de "falhou" — quando falha, mostra o `ContaNaoAbriu` com dois botões: tentar
outra vez e sair.

**2. O painel mostrava o prazo mais LONGE.** Dizia
*"próximo prazo: em 348 dias, 20 de agosto de 2027"* quando a próxima
obrigação era o dia 20 desse mesmo mês:

```
tipo                  data_limite   estado     valor
ss_pagamento          2026-09-20    pendente   269.64
irs_pagamento_conta   2026-09-20    pendente   536.28
ss_pagamento          2026-10-20    pendente   269.64
```

A causa é uma armadilha do cliente do Supabase: em postgrest-dart,
`order(coluna)` tem `ascending = false` por omissão. Escrito assim:

```dart
    bool ascending = false,   // postgrest-2.9.1, postgrest_transform_builder.dart:104
```

Todas as chamadas `.order('...')` sem a direcção devolviam a lista ao
contrário. Corrigidas todas em `lib/`, e `test/unit/ordem_test.dart` falha se
alguém voltar a escrever `.order()` sem dizer a direcção.
